3. Repair concrete interaction defects

Unchanged color edits currently change the palette:
ColorControl.commit (around lines 57–63) calls onChange for any valid value, even if unchanged. updateProfile in front-end/src/theme/appearance.js (around line 108) marks custom=true merely because surface/ink/contrast occurs in the patch. Thus focusing and blurring an unchanged color field can leave the preset path and regenerate the palette. Compare normalized values before committing and make updateProfile ignore no-op field changes. Pressing Enter followed by blur must not double-commit. An untouched field must not enable Reset, change preset/custom flags, write storage, or change colors.

The color picker loses saturation:
ColorControl.choose (around lines 65–93) implements hue/lightness with implicitly full saturation; it does not retain the current color's saturation. Opening a pastel/gray color and changing a picker value can produce an unrelated vivid color. Implement a proper color model with complete round-trip preservation, preferably a small HSV saturation/value plane plus hue rail matching the target interaction. If using existing/native controls, ensure they preserve all channels. Test gray, pastel, black, white and saturated colors. Do not add a large dependency just for this.

Number fields currently bind directly to validated persisted integers and reject all intermediate strings in onChange. Use a local draft so empty/partial edits work naturally; validate on blur/Enter, restore on Escape and keep native stepper/keyboard behavior. Preserve the actual limits 11–16, 12–24 and 8–24. Do not save an invalid intermediate value or shift the entire page during editing.
