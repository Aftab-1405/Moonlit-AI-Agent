P1. Fix the hue-picker interaction model

Confirmed source:
- front-end/src/theme/colorModel.js hexToHsl returns saturation=0 for gray, black and white. Hue has no visible effect when saturation=0; black/white also have no chroma at their lightness extrema.
- AppearanceControls.jsx exposes a Color slider that edits ONLY lightness and a Hue slider that edits ONLY hue. It has no inline saturation control. Both use the ordinary accent-colored MUI slider styling, so the Hue track is not a spectrum.
- The top type=color input opens a second, platform-native picker rather than providing an inline saturation/value plane.
- colorModel.test.js explicitly expects changing hue on #808080 to remain #808080. That math is correct. The missing piece is a usable color-selection workflow, not a need to break neutral color math.

Replace the split native-picker-plus-two-generic-sliders experience with one coherent popover. Prefer an inline saturation/value plane with a hue spectrum rail and hex editing, using an existing suitable component only if already available; otherwise implement the small required control with standard browser/React primitives. No heavy dependency or second nested OS dialog is required. Give the plane a visible selection indicator and the hue rail a rainbow gradient with a visible thumb.

Preserve hue as editing state when the chosen color becomes achromatic. Hex cannot encode a hue for black/gray/white: do not reinitialize the user's selected hue to zero after every neutral-color commit or rerender. Initialize from the external value when opening/changing profiles, but distinguish an external reset from a value echoed after this control's own commit. Choosing a hue while black can legitimately leave the hex black; the rail/plane must still show the selected hue, and raising saturation/value must then yield that hue. Never force full saturation whenever hue changes, which would regress pastel preservation.

Ensure pointer dragging works beyond the plane bounds via pointer capture, coordinates clamp correctly, and touch does not scroll the page mid-gesture. Provide keyboard-accessible equivalent controls and meaningful names/values for the color dimensions. Retain local drafts, normalization, valid-on-commit behavior, no-op suppression, preview cancellation and account scoping. Define pointerup, keyboard commit, blur, backdrop and Escape semantics and prevent a late blur/pointerup from re-committing a cancelled gesture. Avoid duplicate commits from multiple overlapping events.

P2. Preview must correspond to the final edit

Current AppearanceSection creates previewTokens from the effective mode even when editing the other mode's card. It exposes only preview background/ink/secondary/border CSS variables. Custom accent changes therefore do not preview accent-colored controls; editing the inactive profile does not visibly preview that profile. Every preview also forces custom:true, although updateProfile only marks surface/ink/contrast changes custom. This can make an accent preview use a different palette path from its committed result.

Use the same pure update/resolve logic for preview and commit so they agree. Scope each profile preview to the correct card or an explicit preview surface; editing the inactive profile must not switch the whole application's mode. Add accent preview coverage if a custom accent is being edited. Avoid a blanket descendant Typography/input rule that overwrites semantic error colors; preserve validation, disabled, selection and status styling. Test that a settled preview matches the committed profile and that cancellation restores the original UI without changing persisted data.
