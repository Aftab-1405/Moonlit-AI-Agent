Confirmed database-dialog gaps

1. Different layout system. DatabaseModal.jsx uses PreferencePageHeader and PreferenceLayout with the generic, non-settings variants. preferenceSurfaceStyles.js supplies a 96px header, 1380px page cap, 860px content cap and 204px inner navigation. PreferenceLayout also uses large responsive padding and 56/72px column gaps. SettingsModal now uses a compact 24px title, 288px sidebar and 768px outer content cap. Sharing helper names does not mean the layouts are visually consistent.
2. Full-window takeover. DatabaseModal sets left=0, width=100vw, min/max height=100vh and removes the normal dialog width limit. getPreferencePanelPaperSx fixes it over the full window with no corners. It obscures the app rail and uses a transparent backdrop while still being a Dialog. This differs from both the updated Settings surface and ordinary bounded dialogs.
3. Field language mismatch. All credential/URI fields use variant="standard" and floating labels/underlines. The updated appearance/settings UI uses compact outlined controls and quiet bordered groups. Global MuiInput focus-underline overrides further affect this older field style. Use explicit, consistent boundaries and keyboard focus, rather than adding more per-field overrides to the standard variant.
4. Different hierarchy/density. Generic PreferenceSection adds generous section spacing and filled panel styling; rows use the generic striping/density rules. The connection form combines these with Stack gaps and a large footer separator. The provider navigation lacks the deliberate icon/section treatment of the current Settings UI. This is the main code-level explanation for the different visual identity.
5. Accessibility mismatch. DatabaseModal passes disableEnforceFocus to DialogShell and does not supply ariaLabelledBy/ariaDescribedBy. PreferencePageHeader renders a visible heading but has no ID wired to the dialog. Manually focusing the heading does not provide a dialog accessible name or restore focus containment.
6. Unconnected form submission. FieldGrid renders a form without onSubmit or an ID; Connect is outside that form and only has onClick. There is no deliberate Enter-submit path. In particular, investigate implicit browser submission in the single-URI field mode. This is a source-confirmed missing submission contract; actual reload/submission behavior needs a component/browser reproduction.
7. Motion is separately configured. DatabaseModal has mobile Slide, Fade keyed by section, transitionDuration=180, and generic preference helpers impose 300ms opacity transitions. It does not consume useAppearanceReducedMotion. Global CSS shortening alone does not configure MUI transition lifecycle timeouts. Align this component's transition props with the existing resolved preference.
8. Disconnect errors are invisible. handleDisconnect catches and logs failure but does not set the visible error state. The user can click Disconnect and see no explanation on failure. Preserve connection state and show a concise inline failure.
9. Current coverage is too narrow for a visual/form rewrite. databaseModalState.test.js covers button state/style helpers, not form submission, focus, provider switching, URI mode, tab transitions or error rendering. Add real component coverage for the changed behavior.

Focused implementation instructions

Make the database connection dialog cohesive with current Moonlit, without modifying backend APIs, connection payloads, saved-connection semantics or unrelated Settings code. Work from the current unstaged diff and untracked files; preserve staged and unrelated work. Do not deploy, commit, reset or stage changes.

Recommended presentation, a Moonlit design choice rather than a recovered ChatGPT database screen:
- Retain DialogShell and make this a normal bounded dialog on desktop, using its existing md sizing (roughly 800–900px depending on the shared theme), a modest shared corner radius, subtle border and theme overlay. Let the underlying workspace remain visible; it is a focused connection task, not a second Settings application.
- Use full-screen mobile behavior already supported by DialogShell. No horizontal overflow at 390px; controls and actions remain usable with the software keyboard.
- Use the shared compact header with a 24px desktop title, shorter supporting text only if necessary, and canonical close icon. Wire its ID to aria-labelledby. Avoid the oversized generic PreferencePageHeader and redundant text Close button.
- Keep a compact provider selector/navigation with neutral selected styling. Use existing DB_TYPES labels and canonical icons if appropriate; do not introduce colorful logos/new assets just for decoration. At narrow widths, use a wrapping/selectable control that does not overflow rather than compressing the form beside a permanent sidebar.
- Group Connection method and Connection details into quiet rounded sections with consistent borders, typography and spacing. Use compact label/description hierarchy from the current preference components. Do not apply 40px appearance-color-row density blindly to multiline input forms.
- Replace standard inputs with the established outlined control treatment. Keep Host/Port together only where room permits; stack on mobile. Use stable widths, readable helper errors and a consistent input height. Preserve password/URI masking and their accessible show/hide controls.
- Keep Credentials/Connection string and Connection/Databases selection neutral, using the current quiet segmented control styling. Show the Databases view only when an active connection and actual database results exist, as today.
- Use the normal DialogShell footer area where practical. Keep actions visible while only the body scrolls, without covering fields/errors. Connect is an explicit accent action; choose the existing filled action treatment for its ready state. Connecting stays disabled/loading; Connected remains success-styled and disabled. Disconnect retains its semantic danger treatment. Do not recolor success/error states with the user's accent.
- Align empty/loading/error states and the database list with current row/icon/secondary-text conventions. Preserve selected and disabled database semantics and long-name truncation without hiding the accessible name.

Prefer scoped component changes and existing helpers over a new dialog framework. Changing shared preference helpers globally could break Settings and other overlays; add a narrow variant or use DialogShell's existing slots instead. Remove legacy overrides only after confirming their consumers.

Behavior and regression requirements

- Wire an explicit form onSubmit with preventDefault to the validated connect handler. Either place the submit action in the form or link it with the form attribute. All non-submit actions, including show/hide controls and provider selectors, must be type=button. Guard duplicate requests while loading. Verify Enter in URI mode never causes document navigation or leaks form values into a URL.
- Re-enable modal focus containment unless a concrete embedded-control requirement prevents it; document any exception. Initial focus, Tab/Shift+Tab cycling, Escape, nested menus/popovers and focus return to the opener must work. Do not disable focus visibility to make styling look quieter.
- Read the resolved reduced-motion preference for Fade/Slide/Dialog durations; use zero-duration behavior when reduction is active and coherent small transitions otherwise. Avoid redundant opacity animations on both paper and container.
- Preserve provider-specific default ports, supported connection modes, validation, initialDbType, rememberConnection behavior, account namespacing and clearing one provider's credentials before another. Never persist passwords or full URIs as part of this visual refactor.
- Preserve database list handling: actual databases or the connected database fallback; never restore the invalid schemas-as-databases fallback.
- Preserve connection success callbacks, selection callbacks, connection-to-databases transition, and disconnect-to-connection transition. On disconnect failure, display the error and keep the actual connected state.
- Use mocked service responses and synthetic credentials for tests. Do not connect/disconnect a real user database or expose saved credentials in screenshots/logs just to verify layout.
